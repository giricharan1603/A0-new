## 2. Executive Summary & Problem Definition

### 2.1 Problem Statement
Navigating university campuses and localized institutional zones via standard consumer navigation engines (e.g., commercial turn-by-turn map services) often leads to suboptimal routing. These engines frequently miss internal footpaths, pedestrian-only plazas, restricted service roads, and specific landmark-to-landmark shortcuts. Furthermore, academic settings lack clear benchmarking to demonstrate why informed heuristic search (A*) outperforms uninformed uniform-cost algorithms (Dijkstra) in terms of computational overhead on real topological graphs.

### 2.2 Product Vision
The Campus Landmark A* Route Planner is a specialized geospatial routing and analysis engine. It consumes real-world OpenStreetMap (OSM) spatial graphs, snaps arbitrary campus landmarks to network vertices, executes an admissible and consistent A* search using the Haversine distance heuristic, and produces visual, turn-by-turn route maps alongside runtime performance metrics compared against standard Dijkstra search.

### 3.2 Key Performance Indicators (KPIs)
* **Optimality Verification:** 100% agreement between path lengths generated by A* and baseline Dijkstra (ensuring the heuristic is strictly admissible).
* **Efficiency Metric:** A minimum reduction of **40% in nodes expanded** by A* compared to Dijkstra on routes **exceeding 500 meters** (optimized for localized campus scale).
* **Latency:** End-to-end graph extraction and route computation in **< 3.0 seconds** for bounding areas up to $15\text{ km}^2$.
* **Robustness:** Graceful and immediate handling of disconnected graph components, dead ends, and one-way constraints.

## 6. Functional Requirements (FR)

### 6.1 Data Acquisition & Graph Preprocessing
* **FR-1.1:** The system shall fetch geographic network graphs dynamically via OSMnx using either a bounding place query string (e.g., "Madanapalle, Andhra Pradesh, India") or explicit bounding box coordinates (North, South, East, West).
* **FR-1.2:** The system shall support selectable network modes: `drive` (motorized road network) and `walk` (pedestrian paths, walkways, and stairs).
* **FR-1.3:** The graph builder shall preserve directional edge attributes, specifically handling one-way restrictions (`oneway=True/False`) and segment lengths (length in meters).
* **FR-1.4:** Graph data must be cached locally to disk (`.graphml` format) to prevent redundant API calls and rate-limiting issues.
* **FR-1.5:** **[Revised]** The system shall pre-process and convert the `MultiDiGraph` into a simplified standard `DiGraph` prior to running any search algorithm. For multiple edges existing between identical vertices $u$ and $v$, the preprocessing pipeline must retain only the single edge containing $\min(\text{length})$, moving this execution overhead away from the core search loop.

### 6.2 Coordinate Snapping & Geocoding
* **FR-2.1:** The system shall maintain a catalog of pre-configured campus landmarks with hardcoded (latitude, longitude) coordinates.
* **FR-2.2:** The system shall implement a nearest-node resolution function utilizing spatial indexing (KD-Tree or BallTree via OSMnx/scipy) to snap input coordinates to valid graph vertices.
* **FR-2.3:** Snapping distance thresholds must be enforced: warn the user if the nearest reachable road node is $> 250\text{ meters}$ away from the designated coordinate.

### 6.3 Algorithmic Core (A* Implementation)
* **FR-3.1:** The core routing logic must be implemented from base principles using Python’s `heapq` module (min-priority queue) rather than relying exclusively on black-box wrappers.
* **FR-3.2:** **[Revised]** The cost function $g(n)$ shall sum true edge lengths in meters directly from the pre-processed simplified graph structure.
* **FR-3.3 (Heuristic Function $h(n)$):** The heuristic must compute Great-Circle distance using the Haversine formula across latitude/longitude pairs:
  $$d = 2R \arcsin\left(\sqrt{\sin^2\left(\frac{\Delta \phi}{2}\right) + \cos(\phi_1)\cos(\phi_2)\sin^2\left(\frac{\Delta \lambda}{2}\right)}\right)$$
  where $R = 6,371,000\text{ meters}$.
* **FR-3.4 (Heuristic Properties):** $h(n)$ must be strictly admissible ($h(n) \le h^*(n)$) and consistent ($h(n) \le c(n, a, n') + h(n')$) to guarantee optimal solutions without re-opening closed nodes.
* **FR-3.5:** Path reconstruction must be maintained via a predecessor map (`came_from`), returning an ordered list of node IDs from origin to target.
* **FR-3.6:** **[Added]** The routing engine shall verify structural connectivity via a strongly connected component checklist before executing an A* or Dijkstra search to instantly abort queries targeting disjoint networks.

### 6.4 Benchmarking & Profiling Engine
* **FR-4.1:** The system shall execute an uninformed Dijkstra baseline on identical queries by forcing $h(n) = 0$.
* **FR-4.2:** The engine shall capture and output comparative execution metrics:
  * Total path length (meters / kilometers)
  * Total number of nodes expanded (closed set count)
  * Maximum frontier size during search (priority queue peak)
  * Computation latency (wall-clock time in milliseconds)

### 6.5 Output & Visualization
* **FR-5.1:** Produce high-resolution static route visualizations using matplotlib overlaying the graph edges and nodes.
* **FR-5.2:** Render interactive HTML maps using folium, marking:
  * Start landmark (Green pin)
  * Target landmark (Red pin)
  * Calculated optimal trajectory (Colored path polyline)
* **FR-5.3:** Provide a tabular summary on the console detailing turn/node steps, cumulative distances, and comparative metrics.

## 7. Non-Functional Requirements (NFR)
* **Performance:** Path calculations over graphs of up to $50,000\text{ edges}$ must complete within $\le 500\text{ ms}$ on consumer hardware (e.g., standard quad-core CPU).
* **Reliability:** If origin and target exist in disjoint graph subcomponents, the system must terminate cleanly during the connectivity check phase and return an informative error message (`"No connected path found between landmarks"`) within $<10\text{ ms}$ without executing an exhaustive queue search or crashing.
* **Maintainability & Clean Code:** Adhere to PEP 8 standards, complete with type hinting (`typing.List`, `typing.Tuple`, `typing.Dict`) and docstrings defining inputs, preconditions, and return values.
* **Portability:** Self-contained environment specification through standard dependency files (`requirements.txt`).
